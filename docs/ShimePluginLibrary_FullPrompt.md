# ShimePluginLibrary 総合開発プロジェクト — 完全実装指示書

あなたは、Minecraftサーバーのプラグイン開発、Paper API、Spigot API、NMS、Kotlin、Java、JVM、Gradle、データベース設計、非同期処理、セキュリティ、API設計、ソフトウェアアーキテクチャに精通した、非常に高度なソフトウェアエンジニアです。

これから、Minecraftサーバー向けの総合プラグイン開発ライブラリ「ShimePluginLibrary」を新規開発してください。

本プロジェクトの目的は、単なるユーティリティ集を作ることではありません。

さまざまな種類のMinecraftプラグインを効率的、安全、簡潔、かつ高品質に開発できる、独立性の高い総合APIを構築することです。

コマンド管理、GUI、アイテム管理、設定ファイル、データベース、プレイヤーデータ、メッセージ、イベント、タスク、NMS、パケット、権限、経済システム、キャッシュ、キャラクター管理、スコアボードなど、実際のプラグイン開発で繰り返し必要になる機能を体系的に整備してください。

さらに、一般的なAPIにありがちな設計上の制約や不足している機能も検討し、ShimePluginLibrary独自の価値を持たせてください。

ただし、機能の数だけを追い求めるのではなく、各機能の完成度、安定性、拡張性、相互運用性、使いやすさを重視してください。

コードを書くだけでなく、実際にビルドでき、他のプラグインから利用でき、ドキュメントに従って導入できる状態まで完成させてください。

# 1. プロジェクトの基本情報

## 1.1 プロジェクト名

ShimePluginLibrary

## 1.2 メインクラス

完全修飾クラス名：

shimeserver.shimepluginlibrary.ShimePlugin

メインクラス名：

ShimePlugin

## 1.3 パッケージのルート

shimeserver.shimepluginlibrary

すべてのパッケージは、このルートパッケージの下に配置してください。

## 1.4 言語

基本言語はKotlinとします。

通常のクラス、マネージャー、サービス、API、ユーティリティ、設定管理、GUI管理、コマンド管理、データ管理などは、原則としてKotlinで実装してください。

ただし、次のようなケースではJavaの使用を認めます。

- Javaで実装したほうがJVMとの相互運用性を確保しやすい機能。
- Javaの標準的なAPIやライブラリとの統合で、Java実装が明確に有利な機能。
- Kotlinで実装するよりJavaのほうが適切な低レベル処理。
- NMSや内部APIとの連携において、対象バージョンの仕様上、Java実装のほうが保守しやすい機能。
- Java向けの公開APIを提供するためにJava実装が適している機能。

ただし、Javaを安易に採用してはいけません。

Javaを使用する場合は、その技術的な理由を説明できる構成にしてください。

Kotlinで十分に実装できる機能を、理由なくJavaへ変更しないでください。

KotlinとJavaが混在しても、ビルド、クラス参照、依存関係、公開APIの互換性に問題が発生しないようにしてください。

## 1.5 ビルドシステム

Gradleを使用してください。

ビルド設定にはGroovy DSLを使用し、原則として `build.gradle` と `settings.gradle` を採用してください。

Kotlin DSLである `build.gradle.kts` は、特別な理由がない限り使用しないでください。

Kotlinのバージョン、Javaツールチェーン、Paper APIのバージョン、各種ライブラリのバージョンは、互換性を確認して明示してください。

依存関係のバージョンを適当に決めたり、存在を確認できないライブラリを追加したりしてはいけません。

## 1.6 Minecraftサーバー

基本的な対象はPaperサーバーとします。

初期開発では、Paper 1.20.6を基準に設計してください。

Java 21を使用し、Paper 1.20.6の仕様に適合する構成を採用してください。

ただし、将来的なMinecraftのバージョン更新に対応しやすい設計にしてください。

NMSを利用する機能は、通常のPaper APIを利用する機能から可能な限り分離してください。

Paper APIだけで実現できる機能について、必要もないのにNMSを利用しないでください。

# 3. 独立したライブラリとしての設計

`ShimePluginLibrary` は共通APIを提供するGradleモジュールです。Minecraftサーバーへ導入するプラグイン本体は、別モジュール `ShimePlugin` が担当します。

`ShimePlugin` が `ShimePluginLibrary`、`ShimePluginCommand`、`ShimePluginNMS` を統合して、サーバーに導入するプラグインJARを生成してください。

## 3.1 メインクラス

メインクラスは次のとおりです。

`shimeserver.shimepluginlibrary.ShimePlugin`

このクラスは `ShimePlugin` モジュールに配置するPaperプラグインのエントリーポイントです。ライブラリ全体の初期化と終了処理を統括し、実際の処理は `ShimePluginLibrary` モジュールの初期化クラスへ委譲してください。

実装する内容：

- プラグイン起動時の初期化。
- 各マネージャーの生成と登録。
- サービスの初期化。
- 設定ファイルの読み込み。
- 必要なストレージの初期化。
- 使用可能な機能の登録。
- 起動時の依存関係チェック。
- 初期化失敗時の適切なエラー処理。
- プラグイン停止時のリソース解放。
- 非同期タスクの終了処理。
- データベース接続やコネクションプールの終了処理。
- リスナーや内部リソースの適切な解除。
- 起動時間や有効化されたモジュールなどの情報表示。

すべての処理をメインクラスに直接実装してはいけません。

メインクラスは初期化を統括し、個別の処理は専用のクラスへ委譲してください。

## 3.2 APIの公開

ほかのプラグインが、ShimePluginLibraryの機能を簡単に利用できるようにしてください。

公開APIは、実装クラスの内部構造に過度に依存しないようにしてください。

利用する側のプラグインが、ShimePluginLibraryの内部実装を直接操作しなくても済むようにしてください。

可能であれば、公開インターフェースと内部実装を分離してください。

APIのバージョニングを考慮し、将来的な機能追加や変更に対応できる設計にしてください。

## 3.3 依存関係

ShimePluginLibraryは、独立したプロジェクトとして成立させてください。

外部API、特定の別プラグイン、別の開発者が作成した独自ライブラリが存在することを前提にしてはいけません。

必要な機能は、ShimePluginLibrary自身で実装するか、適切な外部ライブラリを明示的な依存関係として管理してください。

外部ライブラリを使用する場合は、ライセンス、バージョン、配布方法、クラスローダーとの互換性を確認してください。

# 4. 参考資料の調査と独自実装

開発開始時に、ユーザーが提供する既存APIのソースコード、プロジェクト構成、公開クラス、利用例、設定ファイルなどを調査してください。

そのAPIは、設計の参考資料として扱います。

確認すべき内容：

- パッケージ構成。
- クラスの責務分担。
- マネージャーの設計。
- APIの公開方法。
- 初期化処理。
- 設定ファイルの扱い。
- コマンド登録の仕組み。
- イベント管理。
- GUI実装。
- NMS実装。
- データ管理。
- エラー処理。
- 開発者向けの使いやすさ。
- 既存機能の不足。
- 拡張性や保守性の問題。

参考資料から有用な設計上の考え方を学びつつ、ShimePluginLibrary独自の構成、クラス、API、機能を設計してください。

既存実装の内容を無条件にコピーしてはいけません。

各機能について、次の観点から設計を見直してください。

1. その機能は本当に必要か。
2. APIとして使いやすいか。
3. 複数のプラグインから再利用できるか。
4. Paper APIで十分に実現できるか。
5. NMSが必要な場合、バージョン差異を隔離できるか。
6. 非同期処理による問題が発生しないか。
7. リソース管理が適切か。
8. テストできる構造になっているか。
9. 既存のほかの機能と自然に連携できるか。
10. 将来の機能追加を妨げないか。

既存APIを参考にする目的は、既存の機能を減らすことではありません。

既存APIで実現できていた機能を把握したうえで、必要な機能を維持し、改善し、新しい機能を追加してください。

ただし、参考資料に存在しない機能を、存在するかのように扱ってはいけません。

ソースコードを実際に調査してから設計してください。

## 6.1 モジュールの責務

| Gradleモジュール | 責務 |
|---|---|
| `ShimePlugin` | Paperプラグインのエントリーポイント、`plugin.yml`、起動・終了の統括、最終JARの生成 |
| `ShimePluginLibrary` | GUI、Config、Database、Player、Item、Message、Event、Task、Permission、Economy、Cache、Storage、Scoreboard、Service、Validationなど、共通ライブラリ機能全般 |
| `ShimePluginCommand` | コマンド登録、引数解析、補完、実行コンテキスト、コマンド権限など |
| `ShimePluginNMS` | NMS、バージョン別アダプター、低レベルエンティティ処理、パケット関連処理 |

## 6.2 ShimePluginLibrary内部の機能分割

`ShimePluginLibrary` は単一のGradleモジュールですが、内部のKotlinパッケージは機能別に分割してください。たとえばGUIは `shimegui`、設定は `shimeconfig`、データベースは `shimedatabase` とします。これらを `ShimePluginGUI/`、`ShimePluginConfig/`、`ShimePluginDatabase/` のような独立したGradleサブプロジェクトにしてはいけません。

## 6.3 依存関係

- `ShimePluginLibrary` は共通APIと汎用機能を提供します。
- `ShimePluginCommand` は必要に応じて `ShimePluginLibrary` に依存します。
- `ShimePluginNMS` は必要に応じて `ShimePluginLibrary` に依存します。
- `ShimePlugin` は上記3モジュールを統合し、サーバーに導入するプラグインJARを生成します。
- 循環依存は禁止です。
- Paper APIは各モジュールで必要な範囲に限ってcompileOnly等で参照し、Paper API自体を最終JARへ同梱しないでください。

## 6.4 Gradle設定

ルートの `settings.gradle` には次の4モジュールだけを登録してください。

```groovy
include 'ShimePlugin'
include 'ShimePluginLibrary'
include 'ShimePluginCommand'
include 'ShimePluginNMS'
```

モジュール名、フォルダ名、Gradle project pathは完全に一致させてください。ルート `build.gradle` でKotlin/JVM、Java 21、リポジトリなどの共通設定を管理し、各モジュールの `build.gradle` では固有の依存関係を定義してください。

## 6.5 最終JAR

サーバーに導入する最終プラグインJARは `ShimePlugin` モジュールから生成してください。`ShimePluginLibrary`、`ShimePluginCommand`、`ShimePluginNMS` の必要なクラスを統合し、`plugin.yml` とともに配布可能なJARにしてください。Paper APIは同梱しないでください。Kotlinランタイムや必要な外部ライブラリの同梱方法も明確にしてください。

# 7. APIの基本設計

## 7.1 一貫した利用方法

ライブラリを使用するプラグインの開発者が、複雑な初期化処理を何度も書かなくても済むようにしてください。

各機能の利用方法を統一してください。

ただし、すべての機能を単一の巨大なAPIクラスに押し込めてはいけません。

責務ごとにAPIを分離してください。

## 7.2 マネージャー

機能ごとに専用のマネージャーを提供してください。

例：

- `ShimeCommandManager`
- `ShimeGUIManager`
- `ShimeConfigManager`
- `ShimeDatabaseManager`
- `ShimePlayerManager`
- `ShimeItemManager`
- `ShimeMessageManager`
- `ShimeTaskManager`
- `ShimeEventManager`

## 7.4 ライフサイクル

少なくとも次の状態を区別してください。

- 初期化中。
- 使用可能。
- 停止中。
- 停止済み。
- 初期化失敗。

初期化されていない機能を誤って利用した場合には、原因が分かるエラーを出してください。

- 必要に応じた`@JvmStatic`。
- 必要に応じた`@JvmOverloads`。
- 適切なJava向けファクトリーメソッド。
- Javaから扱いやすいインターフェース。
- 例外の扱い。
- ジェネリクスの公開方法。
- null安全性。
- 非同期処理の利用方法。

Kotlin専用の便利さと、Javaからの利用しやすさのバランスを取ってください。

**これ以外のGradleサブプロジェクトを作成してはいけません。**

GUI、Config、Database、Player、Item、Message、Event、Task、Permission、Economy、Cache、Storage、Scoreboard、Integrationなどは、すべて `ShimePluginLibrary` モジュール内のパッケージとして実装してください。機能ごとにパッケージを分けることと、Gradleモジュールを分けることを混同しないでください。

`ShimePluginCommand` はコマンドAPIを担当し、`ShimePluginNMS` はNMSとパケットなどのバージョン依存処理を担当します。`ShimePlugin` はプラグインのメインクラス、plugin.yml、各モジュールの初期化統括、最終JARの生成を担当します。

依存方向は原則として、`ShimePluginCommand` と `ShimePluginNMS` から必要に応じて `ShimePluginLibrary` を参照し、`ShimePlugin` がそれらを統合する一方向の構成にしてください。循環依存は禁止です。

各モジュールは独立した `build.gradle` と `src` を持つGradleサブプロジェクトにしてください。ルートの `settings.gradle` には上記4つだけを `include` してください。

# 35. ビルドとコード品質

プロジェクト全体で、以下を徹底してください。

- すべてのソースファイルに適切なコメントを記述する。

# 36. 実装時の禁止事項

以下は禁止です。

1. 実装していない機能を、実装済みとして説明する。
2. クラス名だけを作成して、中身を実装しない。
3. TODOだけのメソッドを残す。
4. 仮の戻り値で正常動作を装う。
5. 存在を確認していないAPIを使用する。
6. バージョンを確認せずNMSを実装する。
7. すべての処理をメインクラスへ集中させる。
8. すべての機能を巨大なUtilクラスへ詰め込む。
9. 無意味なManagerクラスを大量に作成する。
10. メインスレッドで重い処理を実行する。
11. Bukkitのスレッド制約を無視する。
12. リソースの終了処理を省略する。
13. SQLに外部入力を直接連結する。
14. 設定ファイルのエラーを無視する。
15. 外部ライブラリの依存関係を無条件に増やす。
16. ビルドできないサンプルコードを作成する。
17. 参考元のAPI名や関連記述を成果物へ混入させる。
18. パッケージ名の接頭辞ルールを破る。
19. プロジェクト独自のソースファイル名の接頭辞ルールを破る。
20. コメントを省略して、保守性を低下させる。
21. 未検証のコードを、動作確認済みとして説明する。
22. テストを実行していないのに、テスト成功と報告する。
23. 依存関係を確認せず、ビルドが成功すると断言する。
24. バージョン依存の実装を共通コードへ無条件に混在させる。
25. APIの破壊的変更を、説明なく行う。
